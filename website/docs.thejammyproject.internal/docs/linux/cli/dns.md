# Linux DNS Guide

DNS maps names to data such as IP addresses, mail servers, and service metadata.

---

# Common Record Types

```text
A       IPv4 address
AAAA    IPv6 address
CNAME   alias to another DNS name
MX      mail exchanger
TXT     arbitrary text, often verification or email policy
NS      authoritative name server for a zone
SOA     zone authority and timing metadata
PTR     reverse lookup
SRV     service location
CAA     permitted certificate authorities
```

---

# Query with `dig`

```bash
dig example.com
dig example.com A
dig example.com AAAA
dig example.com MX
dig example.com TXT
dig example.com +short
```

Ask a particular resolver:

```bash
dig @1.1.1.1 example.com A
```

Trace delegation from the root:

```bash
dig +trace example.com
```

Reverse lookup:

```bash
dig -x 192.0.2.10
```

Query TCP explicitly:

```bash
dig +tcp example.com
```

# System Resolution

Applications normally use the system resolver, which can include `/etc/hosts`, DNS, mDNS, LDAP, and caching services.

```bash
getent ahosts example.com
getent hosts example.com
cat /etc/nsswitch.conf
cat /etc/resolv.conf
resolvectl status
resolvectl query example.com
```

`dig` tests DNS directly; `getent` better reflects what normal applications resolve.

`/etc/resolv.conf` may be generated by NetworkManager, `systemd-resolved`, DHCP, Netplan, or a container runtime. Identify its owner before editing it.

---

# Recursive vs Authoritative DNS

A recursive resolver finds answers on behalf of clients and caches them. An authoritative server publishes the definitive records for a zone.

Find authoritative servers:

```bash
dig example.com NS +short
```

Then query one directly:

```bash
dig @ns1.example.net app.example.com A
```

Comparing the authoritative answer with recursive resolvers can expose propagation, cache, or delegation issues.

# Read a `dig` Response

Important fields include:

```text
status       NOERROR, NXDOMAIN, SERVFAIL, REFUSED
flags        qr, aa, rd, ra, ad, tc
ANSWER       requested records
AUTHORITY    delegation or authority information
TTL          cache lifetime in seconds
SERVER       resolver that answered
```

```text
NXDOMAIN   name does not exist
NOERROR with no answer   name may exist but not with that record type
SERVFAIL   resolver could not complete validation or upstream lookup
REFUSED    server declined the query
```

# Troubleshooting Flow

```bash
getent ahosts app.example.com
resolvectl status
dig app.example.com A
dig @CONFIGURED_RESOLVER app.example.com A
dig example.com NS +short
dig @AUTHORITATIVE_SERVER app.example.com A
dig +trace app.example.com
```

Check:

- Typo and fully qualified name
- `/etc/hosts` override
- Search domains and split DNS
- Expected A and AAAA records
- Delegation and glue records
- TTL and cached old answers
- DNSSEC-related `SERVFAIL`
- UDP/TCP port 53 reachability
- Whether the application uses its own resolver/cache

Flush a `systemd-resolved` cache when justified:

```bash
sudo resolvectl flush-caches
```

Do not treat cache flushing as a substitute for finding incorrect records or TTL behaviour.

# `nslookup`

`nslookup` is widely available:

```bash
nslookup example.com
nslookup -type=MX example.com
```

For detailed DNS diagnosis and scripting, `dig` generally exposes more useful protocol information.
